# Roadmap and progress tracker

**This is the canonical completion checklist for RubyVR Studio and its intended
game integration.** It replaces the local research workspace's
`_docs/full-vr-roadmap-v1.md`; its detailed M0–M11 scope is retained here.
Work-package documents explain individual contributions; they are not another
roadmap. Last reconciled **2026-09-11**: archived PRs #19–#31 and the new
repository's GPL PR #19, camera-driven loading PR #20, ground-base PR #21 and
native Linux/WSL PR #22 are merged.
Experimental foliage art remains unapproved.

**Prefer the short version? [Watch the acceptance GIF and verdict](acceptance.md).**
The contributor/agent performs routine desktop functional and visual checks;
the maintainer can give feedback without repeating the test procedure. Actual
human usability/headset sessions still need a tester and are never inferred
from a GIF. This changes review ownership, not the required quality or scope.

- **[x]** The stated, bounded work is implemented, verified and merged. Evidence
  is linked below. This does not approve an entire milestone or every asset.
- **[ ]** Work or acceptance remains. **In review** means implemented and tested
  in an open PR, with the merge still pending.
- Editor, visual, live-game and headset evidence are separate. A milestone is
  complete only when its exit criteria are met, including any required human
  usability or headset sessions.

There is no whole-game completion percentage: definitions, source families,
placements and gameplay states are different units. A floor or menu can
intentionally remain flat/2D; accidental flat buildings, missing effects and
temporary fallback frames remain defects.

## The finished experience

Play the complete supported Ruby adventure in **Windows PC VR through OpenXR**:
a coherent voxel field world, every map/interior accounted for, animated
characters/effects, correct terrain and water levels, sky/day/night, readable
UI, working battles/special gameplay, reliable saves, comfortable controls and
measured headset performance. Studio must make the remaining art practical to
author and maintain manually.

The initial presentation uses voxel scenery, original animated sprite art for
characters/effects, and deliberate readable UI/battle surfaces. Fully modeled
characters and a complete 3D battle remake add scope. Sapphire requires its own
capture/playthrough validation. Emerald and standalone Quest execution are
separate ports; using a Quest headset connected to a PC is not a standalone app.
A reusable sprite-to-3D core with game-specific adapters is a longer-term
direction; only Ruby is supported today.

## Maintaining this tracker

Each contribution updates its relevant checklist and work package, links
evidence, and names remaining acceptance. Keep work in an open PR unchecked and
mark it **In review**; after verifying the merge, tick only its delivered scope
and update the dashboard/current focus. Do not tick a whole milestone from one
successful fixture. A documentation-only change can explicitly state that no
implementation status changed.

[Work packages](issues/README.md) provide bounded tasks and reproduction;
[GitHub Issues/Milestones](https://github.com/ChronoHaxx/rubyvr-studio/milestones)
track collaboration. Markdown checkboxes and issue states do **not** synchronize
automatically. Keep them consistent when work lands; closing a small issue such
as RV-012 does not close the whole M8 milestone. CI validates repository metadata
and code checks; it cannot certify artistic, gameplay or headset completion.
